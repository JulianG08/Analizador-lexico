1. Gramática ampliada final

Este documento presenta la gramática completa de Paisascript con las tres capas de anotación que el proyecto fue acumulando entrega tras entrega. Las producciones sintácticas originales van en rojo y son idénticas a las de las entregas anteriores. Las reglas semánticas van sobre fondo ámbar. Las reglas de traducción orientada por la sintaxis van en azul.

<produccion> ::= ... — regla original de la gramática (producción sintáctica sin ampliar).

REGLA SEM-x — regla semántica: atributos, dominio de valores y acciones de validación.

REGLA SDT-x — regla de traducción: atributos, acción de generación y la salida que produce en el lenguaje destino.

1.1 Por qué la traducción necesita las otras dos capas

En Gleam Int y Float son tipos disjuntos, con operadores distintos: la suma de enteros es + y la de reales es +.. El operador de concatenación <> exige String en los dos lados. Eso significa que la fase SDT no puede decidir qué emitir mirando solo la forma de la expresión: necesita saber el tipo de cada operando.

Ese tipo lo resolvió el análisis semántico y llega a la fase SDT por dos caminos: la tabla de símbolos, que el traductor recibe ya construida, y el atributo sintetizado type, que el analizador anotó sobre cada nodo de expresión del árbol. Las tres capas del documento no son tres documentos pegados: la azul se apoya en la ámbar, que se apoya en la roja.

REGLA SDT-12 — Listas vacías (ε) y producciones recursivas

Nodos de la gramática: <lista_declaraciones>, <lista_sentencias>, <param_resto>, <arg_resto>, <lista_casos_resto>, <rama_sino>, <paso_opcional>, <tipo_opcional>, <expr_o_p> … <expr_potencia_p>

Atributoscode: sintetizado en cada nodo de la lista.
heredado_izq: en las colas de expresión (<expr_X_p>), el código y el tipo del operando izquierdo bajan como atributo heredado, porque la gramática está factorizada a la derecha para ser LL(1).
Acción de traducciónLa gramática es recursiva por la derecha, así que cada lista tiene una producción vacía. Las reglas son uniformes:
Producción ε → code ← "". No emite nada. En <rama_sino> vacía la acción emite False -> Nil, porque un case de Gleam debe cubrir todos los casos. En <paso_opcional> vacío, paso ← 1. En <tipo_opcional> vacío el tipo se infiere de la expresión.
Producción recursiva → code ← code(elemento) ‖ code(resto): se concatena el elemento con el resultado de la cola, separando con salto de línea las sentencias y con coma los parámetros y argumentos.
Colas de expresión → A' ::= op B A' se resuelve pasando el resultado parcial hacia la derecha como atributo heredado, de modo que a - b - c se asocie a la izquierda, como corresponde.
Salida en Gleam<lista_sentencias> ::= ε → no emite nada.
<rama_sino> ::= ε → False -> Nil
<paso_opcional> ::= ε → paso 1 → list.range(a, b)
<sentencia> ::= <sent_declaracion>
| <sent_lectura>
| <sent_impresion>
| <sent_si>
| <sent_mientras>
| <sent_para>
| <sent_repita>
| <sent_pillemos>
| <sent_retornar>
| <sent_llamada>

REGLA SEM-1 — Declaración de variable y compatibilidad de tipos

Nodos de la gramática: <sent_declaracion>, <tipo_opcional>, <expresion>

Atributos involucradostipo_declarado: heredado desde <tipo_opcional>. Dominio: {numerito, quebradito, cuento, siono} ∪ {⊥}, donde ⊥ = sin anotación.
type(expr): sintetizado en <expresion>. Dominio: {numerito, quebradito, cuento, siono} ∪ {error}.
tipo_simbolo: sintetizado en <sent_declaracion>. Es el tipo con el que el identificador entra a la tabla de símbolos.
RestricciónSi tipo_declarado ≠ ⊥, entonces type(expr) = tipo_declarado.
Si tipo_declarado = ⊥, se infiere tipo_simbolo = type(expr) (como el let de Gleam).
Acciones del compilador1. Calcular type(expr) recorriendo la expresión (atributo sintetizado).
2. Comparar con tipo_declarado. Si difieren, reportar error con fila, columna, lexema y mensaje descriptivo.
3. Insertar el símbolo en el ámbito actual con su tipo, estado de inicialización = verdadero y posición de declaración.
4. El shadowing (redeclaración en el mismo ámbito) es válido: crea un enlace nuevo, no modifica el anterior.
5. Continuar el análisis (recuperación).

REGLA SDT-3 — Declaración de variable

Nodos de la gramática: <sent_declaracion>, <tipo_opcional>

Atributosid.lexema: heredado del token.
code(expr) y type(expr): sintetizados en la expresión; el tipo lo resolvió el análisis semántico y queda anotado en el nodo.
entorno: heredado; la tabla de tipos vivos que la fase SDT va alimentando.
Acción de traduccióncode ← "let " id.lexema " = " code(expr)
1. Emitir el enlace con let.
2. Registrar entorno[id] ← type(expr), porque las acciones posteriores necesitan ese tipo para elegir operadores.
3. La redeclaración del mismo nombre es válida: en Gleam let crea un enlace nuevo (shadowing), que es justo la semántica de Paisascript.
Salida en Gleampille_pues numerito x = 5  →  let x = 5
<tipo_opcional> ::= <tipo>
| e
<sent_lectura> ::= escuche_pues "(" IDENTIFICADOR ")"

REGLA SEM-2 — Uso de identificadores: declaración previa y visibilidad

Nodos de la gramática: <expr_primaria> (IDENTIFICADOR), <sent_lectura>

Atributos involucradosid.lexema: heredado del token IDENTIFICADOR.
id.type: sintetizado desde la tabla de símbolos. Dominio: {numerito, quebradito, cuento, siono, desconocido} ∪ {error}.
id.declarado: sintetizado. Dominio: {verdadero, falso}.
Restricciónid.declarado = verdadero: todo identificador usado en una expresión debe existir en el ámbito actual o en alguno de sus ancestros (alcance léxico anidado).
escuche_pues(id) declara el identificador si no existe y lo marca como inicializado.
Acciones del compilador1. Recorrer la pila de ámbitos de dentro hacia afuera buscando el lexema (resolución de nombres).
2. Si no aparece, reportar «identificador no declarado» con fila, columna y lexema.
3. Si aparece, sintetizar id.type con el tipo del símbolo; si es una función usada sin paréntesis, reportarlo.
4. En <sent_lectura>, declarar/inicializar el identificador y continuar.

REGLA SDT-4 — Lectura de consola, con conversión de tipo

Nodos de la gramática: <sent_lectura>

Atributosid.lexema: heredado.
id.type: consultado en la tabla de símbolos que construyó el análisis semántico.
Acción de traduccióncode ← "let assert Ok(" id ") = erlang.get_line(\"\")"
1. Pedir el módulo gleam/erlang.
2. La consola entrega String. Si la tabla de símbolos dice que la variable es numerito o quebradito, añadir la conversión, porque Gleam no convierte de forma implícita:
let assert Ok(x) = int.parse(string.trim(x))
3. Si el tipo es desconocido, la variable queda como cuento.
Salida en Gleamescuche_pues(edad) con edad: numerito →
let assert Ok(edad) = erlang.get_line("")
let assert Ok(edad) = int.parse(string.trim(edad))

REGLA SDT-5 — Impresión por consola

Nodos de la gramática: <sent_impresion>

Atributoscode(expr) y type(expr): sintetizados.
Acción de traduccióncode ← "io.println(" aCadena(code(expr), type(expr)) ")"
La función auxiliar aCadena es la misma de SDT-9: io.println solo acepta String, así que un numerito pasa por int.to_string, un quebradito por float.to_string y un siono por bool.to_string.
Salida en Gleamhable_pues(total) con total numerito →

REGLA SDT-13 — Llamada a función y cierre de bloque

Nodos de la gramática: <sent_llamada>, <argumentos>, <arg_resto>, <sufijo_id>, <bloque>

Atributosnombre: heredado.
args: sintetizado recorriendo la cola <arg_resto>.
ultima: sintetizado en <bloque>; indica si la última línea del bloque es una expresión o un enlace.
Acción de traduccióncode ← nombre "(" args ")", con los argumentos separados por coma. Una llamada vale igual como sentencia que como expresión, porque en Gleam todo es expresión.
Cierre de bloque: en Gleam todo bloque DEVUELVE un valor, así que no puede terminar en let. Si la última línea traducida es un enlace, la acción añade Nil, que es el valor unitario. Sin esto el código generado no compilaría.
Salida en Gleamsumar(1, 2)  →  sumar(1, 2)
un bloque que termina en let x = 5 recibe una línea Nil al final.

REGLA SDT-6 — Condicional y reestructuración del retorno anticipado

Nodos de la gramática: <sent_si>, <rama_sino>, <sent_retornar>

Atributoscode(cond), code(entonces), code(sino): sintetizados.
continuacion: heredado. Es la lista de sentencias que vienen DESPUÉS del condicional. Es el atributo que hace posible eliminar el retorno anticipado.
Acción de traducciónCaso general:

Sin esta transformación las dos ramas del case tendrían tipos distintos y el código no compilaría.

… resto …
se convierte en
case n < 2 {
  True -> { False }
  False -> { … resto … }
}

REGLA SEM-4 — Condición de control de tipo booleano

Nodos de la gramática: <sent_si>, <sent_mientras>, <sent_repita>

Atributos involucradostype(cond): sintetizado en la expresión de control. Dominio: tipos del lenguaje ∪ {desconocido, error}.
cond_esperado: heredado desde la construcción. Dominio: {siono}.
Restriccióntype(cond) = siono en si_acaso, en mientras_que y en el hasta_que de repita_pues. Una condición numerito, cuento o quebradito no es válida.
En repita_pues la condición se evalúa en el ámbito del cuerpo, así que puede leer las variables que el cuerpo creó.
Acciones del compilador1. Evaluar el tipo sintetizado de la condición.
2. Compararlo con siono.
3. Si no coincide, reportar «la condición debe ser siono» con fila, columna y lexema.
4. Analizar igualmente ambos bloques (recuperación).

REGLA SDT-7 — Bucle de condición al principio → recursión de cola

Nodos de la gramática: <sent_mientras>

Atributosestado: sintetizado del cuerpo. Variables que el cuerpo vuelve a enlazar Y que ya existían fuera: son las únicas que cambian de una vuelta a otra.
libres: sintetizado. Variables que el bucle solo LEE y vienen de fuera.
tipos: de la tabla de símbolos, para anotar la firma.
continuacion: heredado (ver SDT-6).
Acción de traducciónGleam no tiene while: se genera una función auxiliar recursiva de cola, que el BEAM ejecuta en espacio constante.
1. Calcular estado y libres. Los dos entran como parámetros; solo el estado se devuelve.
2. Emitir fn bucle_k(libres, estado) -> T { case cond { True -> { cuerpo; bucle_k(…) } False -> estado } }.
3. En el punto de la llamada: let estado = bucle_k(libres, estado).
4. Si el cuerpo contiene un entregue_pues, la rama False recibe la continuación y la auxiliar devuelve el valor de la función que la contiene.
Salida en Gleammientras_que i <= n dele_pues … hasta_ahi →
fn bucle_1(n: Int, acumulado: Int, i: Int) -> #(Int, Int) {
  case i <= n {
    True -> { … bucle_1(n, acumulado, i) }
    False -> #(acumulado, i)
  }
}

REGLA SEM-7 — La variable de control del pa_cada es de solo lectura

Nodos de la gramática: <sent_para>, y dentro de su <bloque>: <sent_declaracion>, <sent_lectura>, <sent_asignacion>

Atributos involucradosvar_control.lexema: heredado del IDENTIFICADOR que sigue a pa_cada.
var_control.escribible: heredado hacia el ámbito del bucle. Dominio: {verdadero, falso}; vale falso para la variable de control y verdadero para cualquier otra.
var_control.categoria: sintetizado al declararla. Dominio: {bucle}.
var_control.type: sintetizado = numerito.
RestricciónNinguna sentencia del cuerpo puede volver a enlazar la variable de control: ni pille_pues i = …, ni escuche_pues(i), ni i = ….
El atributo se consulta antes de cada redefinición: solo se admite si escribible = verdadero.
Fuera del bucle el nombre vuelve a estar libre, porque el ámbito del pa_cada se cierra al terminar.
Acciones del compilador1. Al entrar al pa_cada, abrir un ámbito nuevo e insertar la variable de control con categoría = bucle, tipo = numerito, inicializada = verdadero y escribible = falso.
2. En cada pille_pues y cada escuche_pues del cuerpo, buscar el nombre en la pila de ámbitos y leer su atributo escribible.
3. Si es falso, reportar error con fila, columna y lexema, y sugerir otro nombre para la variable nueva.
4. Cerrar el ámbito al salir del bucle y continuar.
Por qué importa para Gleam: la variable de control se vuelve el parámetro de fn(i) { … } dentro de list.each; reenlazarla rompería el recorrido.

REGLA SDT-8 — Bucle con contador → list.range o recursión

Nodos de la gramática: <sent_para>, <paso_opcional>

Atributosvar: heredado, la variable de control.
code(desde), code(hasta): sintetizados.
paso: sintetizado de <paso_opcional>; vale 1 cuando la producción deriva en ε (ver SDT-12).
Acción de traducciónHay dos caminos, y la elección depende del paso:
paso = 1 → la forma idiomática de Gleam:
list.range(desde, hasta) |> list.each(fn(var) { cuerpo })
Pide el módulo gleam/list.
paso ≠ 1 → list.range de Gleam NO admite incremento, así que se genera recursión de cola con la comparación orientada según el signo del paso (<= si avanza, >= si retrocede).
Salida en Gleampa_cada k desde 0 hasta 10 de_a 2 dele_pues … listo_pues →
fn bucle_2(k: Int) -> Nil {
  case k <= 10 {
    True -> { … bucle_2(k + 2) }
    False -> Nil
  }
}
<paso_opcional> ::= de_a <expresion>
| e

REGLA SEM-8 — Paso del pa_cada distinto de cero y recorrido alcanzable

Nodos de la gramática: <sent_para>, <paso_opcional>

Atributos involucradosvalor(desde), valor(hasta), valor(paso): sintetizados por plegado de constantes sobre cada <expresion>. Dominio: ℤ ∪ {⊥}, donde ⊥ significa «no es un literal» (admite el menos unario y los paréntesis).
paso_implicito: heredado; vale 1 cuando <paso_opcional> deriva en ε.
direccion: sintetizado en <sent_para> = signo(valor(paso)). Dominio: {+1, −1}.
Restricciónvalor(paso) ≠ 0: con paso 0 la variable de control nunca avanza.
Si valor(paso) > 0 entonces valor(desde) ≤ valor(hasta).
Si valor(paso) < 0 entonces valor(desde) ≥ valor(hasta).
Las dos últimas solo se exigen cuando los tres valores son literales: con límites variables el recorrido no es decidible en tiempo de compilación y la regla calla en lugar de dar un falso positivo.
Acciones del compilador1. Plegar las tres expresiones a su valor constante; si <paso_opcional> es ε, usar paso_implicito = 1.
2. Si valor(paso) = 0, reportar error sobre el lexema del paso con fila y columna.
3. Si los tres son literales, comparar el signo del paso con el orden de los límites y reportar «el cuerpo nunca se ejecuta» indicando los tres valores concretos.
4. Si alguno no es literal, no reportar nada y seguir.
5. Continuar con el cuerpo del bucle.
Por qué importa para Gleam: list.range no admite paso, así que con paso ≠ 1 el generador emite recursión de cola; un paso 0 produciría una recursión infinita.

<bloque>

REGLA SEM-6 — Terminación del bucle: la condición tiene que poder cambiar

Nodos de la gramática: <sent_mientras>, <sent_repita>

Atributos involucradosleidas(cond): sintetizado en la expresión de control. Dominio: conjunto de identificadores que la condición consulta (sin los nombres de función).
redefinidas(cuerpo): sintetizado en <bloque>. Dominio: conjunto de identificadores que el cuerpo vuelve a enlazar con pille_pues o escuche_pues.
valor(cond): sintetizado por plegado de constantes. Dominio: {sizas, naranjas} ∪ {⊥} (⊥ = no constante).
continua_si: heredado de la construcción. Dominio: {verdadero} para mientras_que, {falso} para repita_pues, porque hasta_que es la condición de SALIDA, no de permanencia.
Restricciónvalor(cond) ≠ continua_si: la condición no puede ser el literal que mantiene el bucle vivo (mientras_que sizas o hasta_que naranjas).
leidas(cond) ≠ ∅: una condición sin variables tiene siempre el mismo valor.
leidas(cond) ∩ redefinidas(cuerpo) ≠ ∅: el cuerpo debe redefinir al menos una de las variables que la condición lee.
La regla es conservadora y sólida en este lenguaje: Paisascript es inmutable y sin efectos laterales, así que si esa intersección es vacía ninguna ejecución puede cambiar el valor de la condición.
Acciones del compilador1. Plegar la condición: si es un literal booleano, compararlo con continua_si y reportar «el bucle nunca termina».
2. Recorrer la condición y recolectar leidas(cond), descartando los identificadores que la tabla de símbolos marca como función.
3. Recorrer el cuerpo (incluidos los bucles anidados) y recolectar redefinidas(cuerpo) a partir de los nodos <sent_declaracion>, <sent_lectura> y <sent_asignacion>.
4. Intersecar ambos conjuntos. Si el resultado es vacío, reportar error con fila, columna y lexema del bucle, nombrando las variables de la condición que habría que hacer avanzar.
5. Continuar el análisis del resto del programa.
Por qué importa para Gleam: ese bucle se traduce a una recursión de cola; sin progreso, la función auxiliar nunca alcanza su caso base.

REGLA SDT-9 — Bucle de condición al final → cuerpo antes del case

Nodos de la gramática: <sent_repita>

AtributosLos mismos de SDT-7: estado, libres, continuacion.
sentido: heredado de la construcción. En repita_pues la condición es de SALIDA, no de permanencia.
Acción de traducciónEs la misma recursión de cola de SDT-7 con dos diferencias, y las dos vienen de la semántica post-test:
1. El cuerpo se emite ANTES del case, no dentro de una de sus ramas. Eso es lo que hace que corra al menos una vez.
2. Las ramas se invierten: True (se cumplió hasta_que) devuelve el estado y es el caso base; False vuelve a llamar.
Salida en Gleamrepita_pues … hasta_que v >= 3 →
fn bucle_3(v: Int) -> Int {
  … cuerpo …

    True -> v
    False -> bucle_3(v)
  }

/* palabra de cierre adicional. La condicion se evalua DENTRO del ambito */
/* del cuerpo, asi que puede leer las variables que el cuerpo acaba de */
/* crear: es el mismo estado que el generador pasa a la recursion de */
/* cola de Gleam. */

REGLA SDT-11 — Operadores: la elección depende del tipo

Nodos de la gramática: <expr_aditiva>, <expr_multiplicativa>, <expr_potencia>, <expr_relacional>, <expr_igualdad>, <expr_concat>, <expr_y>, <expr_o>, <expr_unaria>

3. El compilador: cuatro fases encadenadas

El compilador procesa la entrada en cuatro fases, cada una en su propio módulo, y cada una recibe exactamente lo que produjo la anterior.

#FaseMódulo Qué produce
1Análisis léxicolexer.py Tokens con lexema, fila y columna. Reporta los no reconocidos.
2Análisis sintácticoparser.py El CST según la gramática BNF. Recuperación de errores para seguir analizando.
3Análisis semánticoanalizador_semantico.py Tabla de símbolos y validación de las ocho reglas. Anota el tipo sintetizado sobre cada nodo de expresión.
4Traducción (SDT)traductor_sdt.py Recorre el CST aplicando las acciones SDT y emite el código Gleam.

El encadenamiento lo gobierna compilador.py, que es el único punto donde se decide si hay salida:

from compilador import compilar resultado = compilar(codigo_fuente) if resultado.exitoso: print(resultado.codigo_gleam) else: print(resultado.reporte()) # errores de las tres fases, unificados

3.1 Si hay errores, no hay salida

Es una regla dura del enunciado y está implementada como tal: mientras exista un error léxico, sintáctico o semántico, la fase SDT no se ejecuta y el compilador se limita a reportar. Un error sintáctico además detiene el análisis semántico, porque un árbol roto solo produciría errores falsos.

3.2 Reporte de errores unificado

Las tres fases de análisis entregan sus errores al mismo objeto ErrorCompilacion, con fase, fila, columna, lexema y mensaje descriptivo. Cada fase aplica recuperación, de modo que una sola ejecución reporte el mayor número posible de problemas.

--- Fase SEMÁNTICA (8) --- [SEMÁNTICA] Fila 13, Columna 21 sobre 'edad': [SEM-1] Se declara 'edad' como numerito, pero la expresión es de tipo cuento [SEMÁNTICA] Fila 33, Columna 1 sobre 'mientras_que': [SEM-6] El cuerpo de 'mientras_que' no redefine ninguna variable de la condición (tope): el bucle nunca termina

3.3 La tabla de símbolos durante la fase SDT

El traductor recibe la tabla de símbolos ya construida y la consulta para los tipos de las variables y las firmas de las funciones. Es lo que le permite saber que escuche_pues(edad) necesita int.parse cuando edad es numerito, y que a + b debe emitirse como a +. b cuando los operandos son quebradito.

3.4 Un ejemplo completo

Entrada en Paisascript:

hagale_pues sumatoria(numerito n) pa_que_lleve numerito dele_pues pille_pues numerito acumulado = 0 pille_pues numerito i = 1 mientras_que i <= n dele_pues pille_pues acumulado = acumulado + i pille_pues i = i + 1 hasta_ahi entregue_pues acumulado ya_quedo pille_pues numerito total = sumatoria(10) hable_pues("La sumatoria de 1 a 10 es: " <> total)

Salida que produce la fase SDT:

import gleam/int import gleam/io pub fn main() { let total = sumatoria(10) io.println("La sumatoria de 1 a 10 es: " <> int.to_string(total)) } pub fn sumatoria(n: Int) -> Int { let acumulado = 0 let i = 1 let #(acumulado, i) = bucle_1(n, acumulado, i) acumulado } fn bucle_1(n: Int, acumulado: Int, i: Int) -> #(Int, Int) { case i <= n { True -> { let acumulado = acumulado + i let i = i + 1 bucle_1(n, acumulado, i) } False -> #(acumulado, i) } }

Obsérvense tres decisiones de la fase SDT en este fragmento: el int.to_string que exige la concatenación (SDT-11), el parámetro n que viaja a la función auxiliar porque el bucle lo lee aunque no lo modifique (SDT-7), y la tupla #(acumulado, i) con el estado del bucle, que es lo que reemplaza a la mutación que Gleam no tiene.

4. Bonus — Validación del código generado con IA

Modalidad C: combinación de validación y sugerencias. Una vez que la fase SDT produce el código Gleam, ese texto se envía a un modelo de lenguaje que primero comprueba si es sintáctica y semánticamente correcto para Gleam y, si lo es, propone mejoras concretas.

Es una capa adicional: el compilador funciona completo sin ella, y si no hay clave de API o no hay red, la interfaz lo indica y el resto sigue funcionando igual.

4.1 El prompt
